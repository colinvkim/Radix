**Metadata-only search — 4 September 2026**

[FileSearchService](/Users/colin/Programming/Radix/Radix/Services/FileBrowserSearch.swift:105) now filters existing tree records directly when a query has no text and no valid text index exists. It avoids URL-path processing, text normalization, and parent-group/index allocation for those queries. A valid cached index is still reused; changing the snapshot or tree content ID invalidates it. Matching and the existing cancellable sorter share one result pipeline, with no new cache or persistent state.

The direct path iterates the tree's existing ordered indices, checks cancellation every 256 entries, and excludes nodes without a parent in the active scope. This preserves root exclusion, logical-scope boundaries, unsorted result order, kind classification, and size-filter semantics. Indexed text/path matching is unchanged.

Three paired Release rounds per scenario compared production revision `18a25ce` with the working-tree fix. Both bundles included the same new benchmark. Each invocation used a fresh process, a new search service, and a synthetic tree with 1,000 directories and 1,000,000 files. Before/after ordering alternated, with no overlapping builds or tests. Measurements used the same Apple M5 MacBook Air, 10 cores, 32 GiB RAM, macOS 26.6.2, and Xcode 26.6.

| Cold metadata query, median of three processes | Before | After |
| --- | ---: | ---: |
| All files, including size sorting | 3.737 s | 1.839 s |
| Files larger than `Int64.max`, no matches | 1.787 s | 0.040 s |
| RSS after all-files query | 1,609.4 MB | 1,488.8 MB |
| RSS after no-match query | 1,027.4 MB | 905.8 MB |

The all-files query took 50.8% less time, and the no-match query took 97.8% less time. Post-query resident memory fell by approximately 121 MB in both scenarios. The no-match query's RSS increase from its starting value fell from 121.8 MB to 0.3 MB. These are process-resident-memory measurements, not allocation-event totals; they include tree storage, allocator retention, and any returned result array. RSS was sampled approximately every millisecond, and starting RSS was about 905.6 MB in every process.

The benchmark then repeated the metadata query, issued the first text query, issued a warm text query, and returned to the metadata filter. Index construction is deferred, not made faster:

| Query transition, median | Before | After |
| --- | ---: | ---: |
| First text query after all-files filters | 0.302 s | 2.043 s |
| First text query after no-match filters | 0.308 s | 2.060 s |
| Warm text query, all-files scenario | 0.349 s | 0.352 s |
| Warm text query, no-match scenario | 0.361 s | 0.356 s |
| Repeated no-match filter before text search | 13.9 ms | 40.0 ms |
| No-match filter after text search | 13.9 ms | 14.5 ms |

Repeated selective filters without a text index scan larger tree records, so they can cost more than scanning an already-built compact index. The service intentionally avoids paying the index's initial time and memory cost for those filters. Once text search builds the index, subsequent filters reuse it. The repeated all-files query remained comparable at 1.829 s before and 1.787 s after; sorting dominates that workload.

All 12 invocations passed result-count and ordering checks. Ordered fingerprints matched across variants for every query phase. Separate cold cancellation probes requested cancellation after a yield and a 2 ms delay, without sorting. Every request threw cancellation: return latency including cleanup was 0.342 ms before versus 1.123 ms after for all-files queries, and 0.249 ms versus 0.025 ms for no-match queries. These samples occur at different stages of work and are not worst-case cancellation bounds.
