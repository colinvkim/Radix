**Scanner queue memory — 4 September 2026**

The measurements do not justify adding a pending-work limit yet. The million-file branching fixture retained at most four pending directory listings, while the flat fixture retained its one million-entry listing. Both peaked near 1.3 GB RSS. Scanning their combined two-million-file tree peaked at 2.68 GB, with that peak still resident at completion. A scheduling limit cannot shrink a single directory's listing, and these runs did not demonstrate an accumulating backlog of many listings.

This follow-up adds opt-in diagnostics and benchmark measurements; Release scheduling and enumeration behavior remain unchanged from `b8ad851`. It refines the original audit's proposed backpressure fix: measure a workload with sustained queue accumulation before adding scheduling state. Completed-tree storage, allocator retention, and finalization are stronger candidates for further attribution on these fixtures. RSS alone does not distinguish their individual costs.

Three rounds ran each fixture sequentially in fresh XCTest processes on the same Apple M5 MacBook Air, 10 cores, 32 GiB RAM, macOS 26.6.2, and Xcode 26.6. Each shape ran first with a normal optimized Release bundle and then with a separate optimized bundle compiled with `-DDEBUG` and `RADIX_SCAN_DIAGNOSTICS=1`. The diagnostic bundle supplies queue counts; its timings are not used as shipping throughput measurements. Builds and fixture creation finished before the measurements. Filesystem caches were warm/uncontrolled, not deliberately flushed.

The fixtures contain empty regular files on local APFS, with hidden files included and automatic summarization disabled. Empty files avoid allocating payload data but exercise size-tied name sorting during finalization. Default concurrency was used: five directory traversal workers, five ordinary-leaf preparation workers, and batches of up to 2,048 listing slots. These workers overlap; they are not a single five-task global limit.

MB is decimal. RSS covers the entire process, including XCTest, live scan storage, and allocator retention. Initial RSS was approximately 42.4 MB. Completion is sampled while the snapshot is still retained. This is not an allocation count, a retained-object census, or an isolated tree-store size.

Each peak was identical across the three instrumented runs. Columns report separate maxima, which need not occur together. The combined fixture's three-listing maximum did not mean three million-entry buffers were retained together.

The [queue instrumentation](/Users/colin/Programming/Radix/Radix/Services/ScanEngine.swift:2069) counts each parent directory's shared listing array once, regardless of how many pending requests reference it. Thus 489 requests for the wide directory retain one million entries, not 489 million. It also records the sum of pending request ranges; these slots can include directories in mixed chunks. Range-slot and retained-entry peaks happened to match for these fixtures.

Measurements occur after directory expansion, where pending counts can increase. They cover pending ordinary-leaf requests only. Active workers, listings being enumerated, completed results waiting in the task group, atomic-summary candidates, reusable probe listings, array spare capacity, and completed node storage are outside these counters. The largest-listing metric covers directories expanded normally, not every possible summary/probe listing. Consequently these counts are neither a hard memory bound nor a census of every live metadata buffer. All added scanner instrumentation is inside `#if DEBUG`, and queue traversal occurs only when diagnostics are enabled.

These phase boundaries use receipt of asynchronous progress events, so they approximate the beginning of finalization rather than timing it inside the scanner. The flat fixture had already reached its peak before that sample. The other shapes peaked later. In all cases substantial RSS remained after completion, which a pending-queue policy alone would not explain or resolve.

All 18 invocations passed expected file, directory, and node counts and produced zero warnings. Additional result checks confirmed shared-buffer accounting for the wide fixture and the relationship between retained listings and entries in the branching fixture. A focused diagnostics test verifies maximum retention and stable report ordering.

Separate Release cancellation probes used the existing full-scan benchmark, requesting cancellation after 250 ms. The branching fixture reached stream termination and summary-pool shutdown in 22.4 ms, and the wide fixture in 4.1 ms. Both observed progress, emitted no finished snapshot, reported no unexpected error, and confirmed summary workers were quiescent. The pool shutdown occurs after traversal task-group exit; this measures more than consumer termination, but does not time release of every remaining allocation. These are single early-traversal samples following a completed scan, not worst-case bounds or tests of cancellation during large sibling sorting.

The full core suite passed: 889 tests, 27 opt-in skips, zero failures. The complete Debug app build succeeded at `.build/xcode-derived-data`, and the diff passed whitespace checks. Review found no need for an additional queue owner, cache, persistence field, or scheduling policy in this change.

These findings apply to the measured regular-file shapes. They do not rule out queue growth with different directory distributions, long paths, package/automatic summaries, slower metadata consumers, or network and provider-backed filesystems. Millions of tiny directories, live SwiftUI memory, completed-scan cache retention, and allocation-event attribution remain unmeasured here. The next memory investigation should distinguish live completed-tree storage from allocator retention and then review the completed-scan cache's soft budget; finalization also warrants a separate CPU/cancellation profile.
